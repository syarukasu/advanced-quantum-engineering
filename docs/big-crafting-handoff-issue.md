# ACO 2.0との連携で巨大注文の実行経路が欠落し、稼働中ジョブも0件と表示される

- Issue: https://github.com/syarukasu/advanced-quantum-engineering/issues/33
- ACO API: https://github.com/syarukasu/ae2-crafting-optimizer/issues/182
- 状態: Ready
- 実装方針: 既存PhysicalCraftingTreeTransactionを公開API経由で使用し、AQEがCPUの提出・tick・保存・取消・完了を担当する。新しい加工エンジンは作らない。

## 対象
- Minecraft 1.20.1 / Forge
- ACO 2.0.0、AQE 2.2.7、Advanced AE 1.3.6、InsaneAE 1.1.0

## 症状と証拠
- BigInteger量子CPUで20段階の圧縮素材を10個発注できるが、利用者からクラフト状況が途中で進まなくなる報告がある。
- 同じ画面で注文と使用中容量が表示される一方、「ジョブ: 0件 (BigInteger 0件)」と表示される。
- ACOの計画完了ログだけでは実加工や納品の完了を証明できない。
- ACO commit 463302897326b07e3b456a762ed191126cf54cf3 はAdvanced AE専用の提出・実行・exact会計のMixinとManagerを削除した。
- AQEのAcoBigCraftingBackendは外部consumerを登録するが、巨大計画の実行を引き継ぐ処理がない。容量連携を許可するだけでは実行対応にならない。
- AQEBigCraftingHost.snapshotはstandardJobCountを0固定にし、ACOアダプターが上書きしていない。導入済みJARのバイトコードでも確認した。

## 修正範囲
- AQEが自分のCPUへの正確な計画の提出、実行、進捗、取消、保存を所有する。
- ACOの既存の物理加工・Receipt精算を再利用し、同じ注文をlong経路と二重実行しない。
- 表示用long投影を実注文数として使わず、実際の加工・受領分だけ残数を減らす。
- ジョブ件数と容量を同じ実予約情報から取得する。
- 通常量のクラフト、レシピ、既存の進行中注文のデータを勝手に書き換えない。

## 受け入れ基準
- long超過の会計が加工、受領、完了まで失われない。
- 受領前に完了扱いにしない。未対応経路を成功として受理しない。
- 稼働中の通常ジョブが0件固定にならない。
- 関連する既存テストとビルドが通る。
- 起動テスト・稼働環境への配置は行わず、未検証として明記する。

## 実装・検証結果
- 容量だけlongを超える注文は、正確な容量を予約した上で元のAdvanced AEへ渡す。
- 素材数・加工回数もlongを超える注文は、AQEが既存物理トランザクションを進める。元のCPUへ同じ加工タスクを重複投入しない。
- 実加工の受領情報を保存し、返却完了後だけ元のクラフトリンクを完了させる。取消も未使用素材・完成済み素材の返却後に閉じる。
- ジョブ件数は容量と同じ予約情報から取得する。「1件なのに0件」の既存テストを修正前に失敗させ、修正後の成功を確認した。
- 関連JUnitは13件成功、1件Skip、失敗0件。SkipはForgeの設定ロード前に実行された既存の任意連携試験で、成功件数には含めない。
- ACO #182のローカルビルドを依存に指定してForgeビルド・難読化変換が成功。新APIが変換後の依存JARへ含まれることも確認した。
- Minecraft起動、実際の20段階注文の完了、取消返却、ワールド再読込、稼働環境への配置は未実施。ゲーム上の解決を確認したとは扱わない。

## 制限と次の確認
- この修正は更新後の新規注文を対象とする。停止済み注文のデータは未変更で、失われた正確な計画を推測して自動復元しない。
- ACO 2.0では#182のAPI追加と組み合わせる。旧2.0開発JARでは巨大注文を受付前に理由付きで拒否する。ACO 1.xでは従来側の実行と二重に動かさない。
- 素材数まで巨大な経路はプレイヤー発注の決定的な作業台レシピが対象。実加工・受領に対応する設備と、入出力両方に対応する監査済みexactセルが必要。
- 今回の変更では機械加工レシピ、液体レシピ、レシピ定義、1.21.1版を変更していない。
- 実ゲーム確認が残るためDraft PRとし、Issueは閉じない。
